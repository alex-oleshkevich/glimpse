# glimpse

A desktop shell suite for Wayland (niri first, Hyprland second): panel, wallpaper, lock screen, plus
standalone providers (notifications, weather, night light, idle) behind typed D-Bus names. No daemon:
`glimpse-panel` owns its services in-process. When unsure, ask "who owns this state?".

Details, reasons and measured facts live in `docs/` — read the relevant file before working there:

| File | When |
| --- | --- |
| `docs/handbook.md` | full conventions, constraints, verification, work rules |
| `docs/live-testing.md` | any run against the real compositor or a second panel |
| `docs/preview.md` | `just preview` and `var/widget_examples/` |
| `docs/translations.md` | locale init, adding a language, extractor traps |

## Layout

| Path | Role |
| --- | --- |
| `crates/` | Flat workspace, one directory per crate |
| `crates/glimpse-applet/` | External applet launcher |
| `sdk/applet/` | TypeScript applet SDK, templates and examples |
| `data/`, `scripts/`, `docs/`, `var/` | Installed assets, local scripts, documentation and scratch files |

`_old/` and `var/glimpse2` are **reference only — never edit, build or copy from them**.

Path-scoped rules load automatically (`.claude/rules/`); skills: `service`, `applet`, `widget`,
`testing`, `live-testing`, `zbus`.

## Hard rules

- **Use `just`, never raw `cargo`.** `just verify` is what CI runs; `just` alone lists recipes.
- **Do not commit or push unless asked.**
- **Write no comments.** Reasoning goes in the crate `README.md`: present-tense rules only — no
  history, measurements, dates, bead ids or current state.
- US English. Never prefix a type with `Glimpse`. Never build a glimpse path by hand — use
  `glimpse-config`'s `user_dir()` / `DATA_DIR`.
- Dependencies are inherited from `[workspace.dependencies]`. **Propose a new crate, never add one
  silently**, with its current version looked up; check `Cargo.lock` first.
- **No `unwrap`/`expect`/blocking call in a service handler.** A slow call moves its reply into
  `ctx.spawn`.
- **Never shell out to `systemctl`, `loginctl`, `nmcli`, `bluetoothctl` or `niri msg`** from glimpse
  code — use D-Bus or the compositor IPC.
- **No service crate has a Wayland dependency.** GTK stays in UI crates or `glimpse-widgets`.
- Runtime state goes under `$XDG_RUNTIME_DIR/glimpse/` only.
- `glimpsectl applets dev`, `install` and `uninstall` may write their documented symlink or applet files under the user's home; tests use a temporary home.
- **Text from other apps is hostile**: cap, ellipsize, never build markup from it.
- **Never add `panic = "abort"`. Never sandbox `glimpse-lock.service`**, and nothing may stop it while
  it holds the lock.
- Mirror services follow the backend and add no policy (exceptions listed in the handbook).
- An applet renders state and sends commands; it never opens D-Bus. UI updates optimistically. A failed
  command is a notification, never a popover banner.
- Mark user-facing strings with `_("…")` / `gettext`, double quotes, named `{placeholders}`.

## Testing

- GTK tests are `#[ignore]`d and only prove anything run one per process: `just test-crate-compositor
  <crate>` or `just test-one <crate> tests::<name>`. Add widget assertions to the end of `widgets()`.
- Never test against `~/.config/glimpse`: pass `--config`, give a test panel a fresh
  `GLIMPSE_PANEL_APP_ID`, kill it by pid — never `pkill -x glimpse-panel`.

## Finishing

Before handing back: `just fmt`, `just verify` clean with zero warnings, delete dead code and
ceremony, fix a README line the change made false. **Docs change rarely**: a README or this file is edited only
when a rule changes, never to describe a feature, record a finding or add history — those live in
beads and git. A change that makes a doc longer must say which paragraph it replaces.
Feature-level plans go through the `plan-precision` skill first.

## Beads Issue Tracker

Use Beads (`bd`) for durable task tracking in repositories that include it. Use the `beads` skill at `.agents/skills/beads/SKILL.md` (project install) or `~/.agents/skills/beads/SKILL.md` (global install) for Beads workflow guidance, then use the `bd` CLI for issue operations.

### Quick Reference

```bash
bd ready                # Find available work
bd show <id>            # View issue details
bd update <id> --claim  # Claim work
bd close <id>           # Complete work
bd prime                # Refresh Beads context
```

### Rules

- Use `bd` for all task tracking; do not create markdown TODO lists.
- Run `bd prime` when Beads context is missing or stale. Codex 0.129.0+ can load Beads context automatically through native hooks; use `/hooks` to inspect or toggle them.
- Keep persistent project memory in Beads via `bd remember`; do not create ad hoc memory files.

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/SYNC_CONCEPTS.md for details and anti-patterns.
