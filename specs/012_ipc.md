# 012 — IPC

The wire between `glimpsed` and every client: frames, the codec, where the socket lives, and both
ends of the transport. `glimpse-ipc` is the crate that holds all of it.

## Problem

One daemon owns every piece of session state and four binaries render it. The connection between
them is the single point where a mistake affects everything at once: a client that reconnects
without resubscribing renders stale data forever, a server that writes synchronously lets one wedged
client stall delivery for the rest, and a codec implemented twice diverges at the first field
anybody adds.

## Goals

- One implementation of the frame format, the codec, the client and the server, so the two ends
  cannot drift.
- A client that survives a daemon restart without its caller writing any recovery code.
- One slow or wedged client cannot delay delivery to any other.
- A round trip is testable without a socket, a daemon or a display.

## Non-goals

- No replay, no message history, no delivery guarantees beyond "the latest value arrives". Topics
  are state cells; a client that missed three intermediate values is not behind, it is current.
- No negotiation. A protocol version mismatch refuses the connection rather than degrading to a
  common subset.
- No authentication or authorisation. The socket is mode 0600 under `$XDG_RUNTIME_DIR`; anything
  that can open it is already running as the user.
- No transport other than a Unix socket. Not TCP, not D-Bus.

## Tech

### The socket

`$XDG_RUNTIME_DIR/glimpse/glimpsed.sock`, mode 0600. The name is
`glimpse_ipc::SOCKET_RELATIVE_PATH` and the path is `glimpse_ipc::socket_path`, so the end that
binds and the end that connects derive it from one constant.

Three rules about where it lives and who may take it:

- **`XDG_RUNTIME_DIR` is required and there is no `/tmp` fallback.** `/tmp` is world-writable, so a
  predictable path there invites socket pre-creation, symlink hijack and cross-user denial of
  service. A session without `XDG_RUNTIME_DIR` is misconfigured, and failing fast is the correct
  response.
- **A second instance fails rather than stealing the socket.** Unlinking an existing socket before
  binding is what lets a second daemon silently displace a live one and leave every connected client
  talking to nothing. Connect first; a socket that answers means a live daemon.
- **A command that could not be delivered returns an error.** A full or closed service channel means
  the command did not take effect, and reporting success for it is worse than reporting failure.

### Frames

Newline-delimited JSON, one frame per line, `{id?, type, data}`.

| Frame                         | Direction | Purpose                                         |
| ----------------------------- | --------- | ----------------------------------------------- |
| `hello` / `hello_ack`         | out / in  | protocol version check, before anything else    |
| `subscribe` / `subscribe_ack` | out / in  | register a pattern, receive matched count       |
| `unsubscribe`                 | out       | drop a pattern, releasing demand                |
| `get` / `get_result`          | out / in  | one-shot read of a topic's current value        |
| `call` / `call_result`        | out / in  | invoke a command, correlated by `id`            |
| `event`                       | in        | `{topic, seq, ts, stale, data}`, the full value |

Errors carry `{code, message, retryable}`. `retryable` is the client's whole decision procedure: it
never inspects the message text.

`seq` is per topic and increases on every published value. It is not a delivery sequence and there
is nothing to resend against it — coalescing means a client legitimately never sees most numbers.
What it gives is an ordering a client can compare, telling a value it already rendered from one it
has not, and a way to see in a log that a service is republishing when it should be gating on
equality. `ts` is when the broker published, not when the backend produced.

A `get` for a topic no service declares is an error. A declared topic with no value yet returns a
result with no value, which is a different answer and a client acts on it differently.

`data` stays `serde_json::Value` at the frame layer. The broker routes topics it has no compile-time
knowledge of, such as `tray.item.{id}`, so typing happens one layer up at the `Topic` boundary.

```rust
pub struct Frame {
    #[serde(skip_serializing_if = "Option::is_none")]
    pub id: Option<u64>,
    #[serde(flatten)]
    pub body: Body,
}

#[serde(tag = "type", content = "data", rename_all = "snake_case")]
pub enum Body {
    Hello { protocol: u32 },
    HelloAck { protocol: u32, daemon_version: String },
    Subscribe { pattern: String },
    SubscribeAck { matched: usize },
    Unsubscribe { pattern: String },
    Get { topic: String },
    GetResult(Status<Option<Event>>),
    Call { command: String, args: serde_json::Value },
    CallResult(Status<serde_json::Value>),
    Event(Event),
}

#[serde(tag = "status", rename_all = "snake_case")]
pub enum Status<T> {
    Ok { value: T },
    Error { error: CallError },
}

pub struct Event {
    pub topic: String,
    pub seq: u64,
    pub ts: u64,
    pub stale: bool,
    pub data: serde_json::Value,
}

pub struct CallError {
    pub code: ErrorCode,
    pub message: String,
    pub retryable: bool,
}

#[serde(rename_all = "snake_case")]
pub enum ErrorCode {
    ProtocolVersion,
    UnknownTopic,
    UnknownCommand,
    InvalidArgs,
    NotReady,
    Unavailable,
    Timeout,
    LimitExceeded,
    Internal,
    #[serde(other)]
    Unknown,
}
```

`Status<T>` is tagged rather than serde's default `Result` shape, which would put `Ok` and `Err`
on the wire as variant names — readable in Rust and strange in Python, TypeScript and Go.

`ErrorCode` carries `#[serde(other)] Unknown` so a code added by a newer daemon deserializes instead
of killing the connection. `retryable` is what a client acts on, so an unrecognised code is still
actionable.

**Payload types accept unknown fields.** A newer daemon and an older client survive a version skew
instead of failing to deserialize — the opposite of the configuration rule, and deliberately so.

### The handshake

`hello` carries `PROTOCOL_VERSION` and must be the first frame. Anything else before it is a
protocol error and the connection closes — a client that skipped the handshake is one whose idea of
the frame set has not been checked. A mismatch is likewise refused and the connection closes.

There is no negotiation and no downgrade. A version bump means frames or topics changed
incompatibly, and a daemon that agreed to speak an older dialect would have to carry every previous
shape forever. One clear message at connect time beats a payload that deserializes into the wrong
shape somewhere later.

`glimpsed` static-asserts `PROTOCOL_VERSION` against its `--version` string, so a bump cannot ship
with stale output.

### The codec

One frame per line, UTF-8, `\n` as the terminator. No length prefix and no framing escape: a JSON
document cannot contain a raw newline outside a string literal, and `serde_json` emits none.

**The framing is `tokio_util::codec::LinesCodec`, not a hand-written one.** Constructed with
`new_with_max_length`, it already implements the line cap and is `Framed`-compatible, which gives
the reader and writer halves for free. `tokio-util` is already a workspace dependency.

What this crate adds on top is two policy decisions the codec deliberately does not make:

- **An over-length line closes the connection.** `LinesCodec` recovers instead: it returns
  `LinesCodecError`, then discards up to the limit and yields `None` until the offending line is
  consumed. Recovering is right for a log tailer and wrong here — a peer that sent an oversize
  frame has a bug or is hostile, and resuming mid-stream means the two ends silently disagree about
  what was delivered.
- **A malformed line closes the connection**, for the same reason. Skipping it and continuing leaves
  no client able to act correctly.

`codec.rs` is therefore thin: `LinesCodec` for the bytes, `serde_json` for the frame, and the two
rules above. It parses and serializes only; it makes no routing decisions.

### Typing

The wire is untyped `serde_json::Value`; types are recovered one layer up.

```rust
pub trait Topic {
    const NAME: &'static str;
    type Payload: Serialize + DeserializeOwned + PartialEq + Send + 'static;
}

pub trait Command {
    const NAME: &'static str;
    type Args: Serialize + Send;
    type Output: DeserializeOwned + Send;
}
```

A dynamic topic — `tray.item.{id}` — has no compile-time name, so it is addressed by string and
typed at the payload boundary with `subscribe_pattern`. That is the whole reason `Frame` carries
`Value` rather than a generic: the broker routes topics it cannot know about.

### The client

`connect`, then the caller subscribes to topics and reads typed values. Everything else is the
client's own problem, not the caller's.

```rust
pub struct Client { /* … */ }

impl Client {
    pub async fn connect(socket: &Path) -> Result<Self, ConnectError>;

    pub fn state(&self) -> ConnectionState;
    pub fn watch_state(&self) -> tokio::sync::watch::Receiver<ConnectionState>;

    pub async fn subscribe<T: Topic>(&self) -> Result<Subscription<T::Payload>, CallError>;
    pub async fn subscribe_pattern(
        &self,
        pattern: &str,
    ) -> Result<Subscription<serde_json::Value>, CallError>;

    pub fn cached<T: Topic>(&self) -> Option<Cached<T::Payload>>;
    pub async fn get<T: Topic>(&self) -> Result<Option<Cached<T::Payload>>, CallError>;
    pub async fn call<C: Command>(&self, args: C::Args) -> Result<C::Output, CallError>;
}

pub enum ConnectionState {
    Connecting,
    Connected,
    Reconnecting { attempt: u32, next_in: Duration },
}

pub struct Cached<T> {
    pub value: T,
    pub seq: u64,
    pub ts: u64,
    pub stale: bool,
}

impl<T> Subscription<T> {
    pub async fn next(&mut self) -> Option<Cached<T>>;
}
```

`Subscription` survives a reconnect: it does not end, and the next value after one is a fresh
snapshot. A caller that treats `next()` returning `None` as "the daemon went away" would be wrong —
`None` means the caller dropped the client.

- **Reconnect with backoff**, and **resubscribe every pattern on reconnect**. This is the entire
  recovery path, because reconnecting equals resubscribing equals a fresh snapshot. A caller writes
  no recovery code and cannot forget to.
- **A typed cache holds the latest value per topic**, handed out through `Topic`. A caller that
  starts mid-session and one that starts at boot read the same thing.
- **`call` results correlate by frame `id`.** A result for an id nobody is waiting on is dropped and
  logged, not treated as an error.
- **While disconnected, the cache keeps the last value it received and does not rewrite `stale`.**
  `stale` is broker metadata meaning the producing service left `Running`, and a client cannot know
  that about a daemon it cannot reach. Connection state is exposed separately, so a caller can dim
  on disconnect without the client inventing a field the daemon owns. Blanking every widget on a
  daemon restart is worse than showing the last known value.

### The server

A listener, then two tasks per client: a reader and a writer. Everything it cannot answer itself it
asks the handler, which in `glimpsed` is the broker.

```rust
#[async_trait]
pub trait Handler: Send + Sync + 'static {
    async fn subscribe(&self, client: ClientId, pattern: &str) -> Result<usize, CallError>;
    async fn unsubscribe(&self, client: ClientId, pattern: &str);
    async fn get(&self, topic: &str) -> Result<Option<Event>, CallError>;
    async fn call(&self, command: &str, args: serde_json::Value)
        -> Result<serde_json::Value, CallError>;
    async fn disconnected(&self, client: ClientId);
}

pub struct Server<H: Handler> { /* … */ }

impl<H: Handler> Server<H> {
    pub async fn bind(socket: &Path, handler: H) -> Result<Self, BindError>;
    pub fn publisher(&self) -> Publisher;
    pub async fn serve(self, shutdown: CancellationToken) -> io::Result<()>;
}

impl Publisher {
    pub fn publish(&self, event: Event);
}

pub enum BindError {
    AlreadyRunning,
    Io(io::Error),
}
```

`publish` never blocks and never fails: it hands the event to each matching client's channel, or
coalesces it against what is already queued there. A client whose channel is over the byte cap is
disconnected by the writer task, not by the caller of `publish` — otherwise the broker learns about
one slow client by being slowed down itself.

`BindError::AlreadyRunning` is the connect-before-bind check, which is what `glimpsed` turns into
exit 3.

- **Writes go to per-client channels.** Nothing writes to a socket from the broker task, because
  anything slow inline hits every client's latency.
- **Newest-value coalescing per client, per topic.** Dropping an intermediate value is lossless when
  every event carries the full value, so a client that reads slowly gets fewer frames rather than
  older ones.
- **A client over its buffered-byte cap is disconnected**, never allowed to stall the loop. The
  client reconnects and resubscribes, which costs it a fresh snapshot and costs everyone else
  nothing.
- **`stale` is set on events for a topic whose service has left `Running`**, so the daemon's honesty
  about upstream reaches the widget rather than stopping at the broker.

Routing is not here. Which client receives which value is the broker's decision and stays in
`glimpsed` — this crate moves bytes and does not choose who gets them.

### Limits

| Limit                        | Value | On breach                         |
| ---------------------------- | ----- | --------------------------------- |
| Maximum line length          | 1 MiB | protocol error, connection closes |
| Buffered bytes per client    | 1 MiB | client disconnected               |
| Subscriptions per client     | 64    | `subscribe` returns an error      |
| In-flight `call`s per client | 32    | `call` returns a retryable error  |

Frames stay small by construction, which is what makes 1 MiB generous rather than tight: tray
pixmaps are decoded to files under `$XDG_RUNTIME_DIR` and referenced by path, so no payload carries
image data. A frame anywhere near the cap means a service is publishing something it should have
written to a file instead.

The four values are constants in one module. A client that hits the subscription cap has a bug —
patterns exist so that one subscription covers a subtree.

### Using it

A battery applet, which is every client in miniature — subscribe, render, and never write a line of
reconnect handling:

```rust
let client = Client::connect(&socket_path).await?;
let mut battery = client.subscribe::<topics::BatteryLevel>().await?;

while let Some(update) = battery.next().await {
    label.set_text(&format!("{}%", update.value.percent));
    label.set_opacity(if update.stale { 0.5 } else { 1.0 });
}
```

The daemon restarting does not break that loop. The subscription is restored, a fresh snapshot
arrives, and the next iteration renders it.

Dimming the whole panel while the daemon is gone is the one thing that needs connection state,
because `stale` cannot say it:

```rust
let mut state = client.watch_state();
while state.changed().await.is_ok() {
    let connected = matches!(*state.borrow(), ConnectionState::Connected);
    root.set_css_class("daemon-gone", !connected);
}
```

A command, sent optimistically — the widget moves first and the topic event reconciles it:

```rust
slider.set_value(target);
if let Err(error) = client.call::<commands::SetVolume>(SetVolumeArgs {
    sink: sink_id,
    volume: target,
}).await {
    tracing::warn!(%error.message, retryable = error.retryable, "set volume failed");
}
```

And the daemon side, which is the whole of `glimpsed`'s socket wiring:

```rust
let server = Server::bind(&socket, BrokerHandler::new(broker.clone())).await?;
let publisher = server.publisher();
broker.set_publisher(publisher);
tokio::spawn(server.serve(shutdown.clone()));
```

`glimpsed` implements `Handler` over the broker and nothing else. There is no listener, no codec and
no per-client bookkeeping in the daemon.

### Testing

A round trip is a unit test in this crate: encode a frame, decode it as the server would, respond,
decode the response as the client would. No socket, no daemon, no display.

That is the reason the client and the server are not separate crates. Split, the only place a real
client met a real server was an integration test over a temporary socket, and the codec had two
homes.

Framing, an oversize line, malformed JSON, reconnect and resubscribe are unit tests here for the
same reason. `002_structure.md` holds the repository-wide testing map.

## Alternatives considered

- **A separate `glimpse-client` crate** — rejected after being specified. See `specs/decisions.md`.
- **Length-prefixed framing** — rejected: NDJSON is greppable, `socat`-able and readable in a
  terminal, which is worth more during development than the parse cost it saves. The line-length cap
  covers the unbounded-buffer risk a prefix would have solved.
- **A binary codec** — rejected: nothing in the payload set is large enough for encoding to register
  against a frame budget. If size ever matters, the codec is negotiated at the handshake, which is
  what the handshake is for.
- **`jsonrpsee`** — rejected on a checked fact, not a preference. It has exactly the subscription
  model this protocol needs, but its transports are HTTP, WebSocket and WASM; there is no Unix
  socket client or server. Running the session bus over a TCP port to reach a library is a worse
  trade than writing the transport.
- **`tarpc`** — rejected: strictly request-response. `ClientMessage` is client-initiated and there
  is no server push, so `event` frames have no expression in it. Its `serde_transport` is generic
  over `AsyncRead`/`AsyncWrite` and would take a `UnixStream`, but the shape of the protocol is the
  mismatch, not the transport.
- **`remoc`** — not pursued: remote channels and RPC over any transport is a superset of what this
  needs, and it brings its own object model. Worth revisiting only if multiplexed typed channels
  become a requirement rather than a convenience.
- **`stubborn-io` for the reconnecting client** — rejected: it reconnects the underlying
  `AsyncRead`/`AsyncWrite` beneath the consumer, which for a `Framed` stream means resuming in the
  middle of a frame. The
  reconnect this protocol needs is not transparent anyway — it has to resubscribe, which no
  transport-level wrapper can know to do.
- **D-Bus as the client API** — rejected: no snapshot-on-subscribe, no per-client coalescing, and
  `stale` would need a value store the bus does not have. See `001_architecture.md`.
- **Replaying missed events after a reconnect** — rejected: topics are state cells, so there is
  nothing to replay. A snapshot is both cheaper and more correct than a backlog.
- **Negotiating down on a protocol mismatch** — rejected: it obliges the daemon to carry every
  previous frame shape indefinitely, and the failure it avoids is one error message at connect time.
